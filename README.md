# confluence-label-bot

Бот-демон для Confluence **Server / Data Center**. Выполняет три независимые
задачи, каждую по своему расписанию:

| Задача | Что делает |
|---|---|
| `moves` | Находит страницы с заданными лейблами в поддереве источника и переносит их под страницу-назначение |
| `mentions` | Собирает людей, отмеченных виджетом `@человек` в заданном столбце таблицы, и складывает их в ячейку-плейсхолдер той же страницы |
| `graphs` | Строит граф зависимостей релизов по таблице раскатки, кладёт картинку на место маркера `<graph_placeholder>`, а под ней JSON плана |

Все настраиваются секциями в `rules.yaml`. Задача включается, если её секция
непустая; ненужные секции можно не заводить.

## Как работает перенос (`moves`)

1. Для каждого правила обходит **всё поддерево** источника на любой глубине,
   рекурсивно спускаясь по `GET /rest/api/content/{id}/child/page`
   (`expand=version,space,metadata.labels`), и отбирает страницы, у которых есть
   любой из указанных лейблов. Регистр лейбла не важен.

   Обход намеренно сделан вместо поиска по CQL: `/content/search` читает из
   Lucene-индекса, который обновляется асинхронно, а в кластере на каждой ноде
   свой — из-за чего CQL умеет молча возвращать неполную выдачу. Обход дерева
   читает из базы и от состояния индекса не зависит.

   Цена — запрос на каждый узел поддерева вместо одного на всё правило. Путь
   предков бот строит по ходу спуска, поэтому `expand=ancestors` не запрашивает
   (на `/descendant/page` он приводил к HTTP 500).
2. Каждую найденную страницу переносит под `target` правила — сменой родителя
   (`PUT /rest/api/content/{id}` с новым `ancestors` и версией +1). Дочерние
   страницы переносятся вместе с ней.
3. Повторяет цикл по расписанию `MOVE_CRON_SCHEDULE`.

Правила применяются по порядку; ошибка одного правила не останавливает остальные.

Операция идемпотентна: после переноса страница выходит из поддерева источника и
на следующих проходах уже не выбирается.

```bash

.venv\Scripts\activate

```

### Правила переноса (`rules.yaml`)

Каждое правило — связка «откуда → куда по каким лейблам»:

```yaml
rules:
  - name: drafts-to-published  # необязательно, для логов
    source: "111111"           # ID страницы-источника: берётся всё её поддерево
    labels: [ready, approved]  # лейблы-триггеры: достаточно любого (ИЛИ)
    target: "333333"           # ID страницы-назначения
    space: DOCS                # необязательно: доп. фильтр по пространству

  - name: archive              # один лейбл можно писать без списка
    source: "222222"
    labels: to-archive
    target: "444444"
```

| Поле | Несколько значений | Смысл |
|---|---|---|
| `source` | нет, ровно один | Откуда: страницы из поддерева этого ID |
| `labels` | да, по ИЛИ | По каким лейблам отбирать |
| `target` | нет, ровно один | Куда переносить |
| `space` | нет, необязательно | Ограничить отбор пространством |
| `name` | нет, необязательно | Имя правила в логах |

`source` и `target` — всегда по одной странице. Для `target` иначе и нельзя:
в Confluence страница не может лежать под несколькими родителями. `source`
дополнительно проверяется на уникальность **между правилами** — одну
страницу-источник обслуживает ровно одно правило, иначе непонятно, куда
переносить подходящую под оба правила страницу.

Файл валидируется при старте: пустые поля, списки в `source`/`target`, `target`,
совпадающий с `source`, повторяющиеся имена правил или источники и опечатки в
названиях полей приводят к понятной ошибке до обращения к API.

### Сбор упоминаний (`mentions` в `rules.yaml`)

На каждой отобранной странице бот читает людей из заданного столбца таблицы и
складывает их в ячейку-плейсхолдер **той же** страницы:

```yaml
mentions:
  - name: release-owners      # необязательно, для логов
    root: "555555"            # ID корня: берутся страницы из его поддерева
    labels: release           # лейблы-триггеры: достаточно любого (ИЛИ)
    column: Ответственный     # заголовок столбца-источника
    placeholder: Участники    # имя строки-приёмника
    space: DOCS               # необязательно: доп. фильтр по пространству
```

| Поле | Несколько значений | Смысл |
|---|---|---|
| `root` | нет, ровно один | Откуда: страницы из поддерева этого ID |
| `labels` | да, по ИЛИ | По каким лейблам отбирать подстраницы |
| `column` | да, объединением | Заголовки столбцов-источников |
| `placeholder` | нет, ровно один | Имя строки-приёмника |
| `space` | нет, необязательно | Ограничить отбор пространством |
| `name` | нет, необязательно | Имя правила в логах |

**Плейсхолдер создаётся руками** — бот не дописывает разметку в чужие страницы.
Нужна строка таблицы, в первой ячейке которой стоит имя плейсхолдера; бот
перезаписывает её вторую ячейку:

```
| Участники |          |  ← бот пишет сюда
| Статус    | В работе |
```

Подойдёт и таблица внутри макроса Page Properties — тогда Page Properties Report
соберёт сводку по подстраницам сам. Первая ячейка читается и как `th`, и как
`td`, поэтому левый столбец Page Properties годится.

Регистр и лишние пробелы в именах столбца и плейсхолдера не важны; `&nbsp;`,
которыми Confluence набивает ячейки, тоже. Заголовком считается первая строка
таблицы, и `th` и `td` равноправны. Если столбец или плейсхолдер на странице не
нашлись, страница пропускается с предупреждением в логе. Если строк с таким
плейсхолдером несколько, берётся первая — и об этом тоже пишется предупреждение.

Что ещё стоит знать:

- **Пустой столбец очищает плейсхолдер.** Иначе выбывший из таблицы человек
  остался бы в нём навсегда.
- **Лишних записей нет.** Перед записью состав сверяется с тем, что уже лежит в
  ячейке, по опознавателям людей. Совпало — запроса на запись не будет. Это
  важно: задача ходит по cron, и каждая запись — это новая версия страницы и
  письмо «вас упомянули» всем из таблицы.
- **Правки помечаются как minor** (`minorEdit`), чтобы не попадать в ленту
  наблюдателям страницы.
- **Первый проход всё равно разошлёт уведомления** тем, кого бот впервые
  поставил в плейсхолдер. Начните с `MENTIONS_DRY_RUN=true`.
- Меняется **только ячейка плейсхолдера**: остальное тело страницы остаётся
  байт-в-байт, поэтому в истории версий виден минимальный diff.
- Один и тот же плейсхолдер в одном поддереве нельзя занять двумя правилами —
  они бы затирали друг друга через проход.
- Упоминанием считается только стандартный виджет (`<ac:link><ri:user …/></ac:link>`).
  Тот же `ri:user` в параметрах макросов не трогается.
- `colspan` и `rowspan` учитываются, так что объединённые ячейки в соседних
  столбцах не сбивают отбор. Таблица внутри ячейки разбирается как отдельная.

### Граф зависимостей релизов (`graphs` в `rules.yaml`)

Код задачи — пакет `confluence_label_bot/release_graph`, перенесённый из
проекта confluence-release-graph (`relgraph`): тот же разбор таблицы, то же
планирование по волнам, тот же встроенный рендерер и та же вставка картинки на
место маркера. Не перенесены CLI, собственный REST-клиент (задача ходит через
общий клиент бота — ради общего троттлинга), Mermaid, mermaid-cli и Kroki.

```yaml
graphs:
  - name: release-graph         # необязательно, для логов
    root: "555555"              # ID корня: берутся страницы из его поддерева
    labels: release             # лейблы-триггеры: достаточно любого (ИЛИ)
    placeholder: graph_placeholder  # необязательно, это значение по умолчанию
    attachment: release-graph.png   # необязательно; .png или .svg
    width: 900                  # необязательно: ширина картинки на странице
    space: DOCS                 # необязательно: доп. фильтр по пространству
```

Что нужно на странице:

- **Таблица раскатки** — первая таблица, в заголовке которой есть столбцы
  `Релиз`/`Release` и `Зависимость от релизов`/`Depends on`. Необязательные
  столбцы и распознаваемые статусы — те же, что в relgraph (полный список в
  `release_graph/parsing.py` и `release_graph/model.py`).
- **Маркер** `<graph_placeholder>` там, где нужен граф. Распознаются все виды, в
  которых его хранит Confluence: `&lt;graph_placeholder&gt;` (так сохраняет
  редактор), `<graph_placeholder />`, `<ac:placeholder>graph_placeholder</ac:placeholder>`.

Что делает проход по странице:

1. Читает текущее тело, разбирает таблицу, строит план.
2. Ставит `<ac:image>` с вложением на место маркера. Маркера уже нет — находит
   свою картинку по имени вложения.
3. Сразу под картинкой ставит свёрнутый макрос `code` с заголовком
   `release-graph.json` (по имени вложения) — в нём `{"rows": …, "plan": …}`, то
   же, что relgraph пишет в `plan.json`. Если макрос уже есть, обновляет его на
   месте.
4. Заливает картинку вложением (новой версией, если такое уже есть) и
   сохраняет тело как minor edit.

Что ещё стоит знать:

- **Лишних записей нет.** Если JSON на странице совпадает с новым планом и тело
  менять не нужно, страница пропускается целиком — без новой версии страницы и
  без новой версии вложения. В relgraph каждый запуск заливал новую версию
  вложения; по cron это плодило бы их на каждом проходе. План однозначно задаёт
  картинку, поэтому сравнивается именно он, и сравнивается по данным, а не по
  тексту макроса: Confluence при сохранении переписывает его атрибуты.
- **Нет ни маркера, ни картинки** — страница пропускается с предупреждением.
  Нет таблицы раскатки — тоже.
- **Ошибки плана** (цикл, дубли релизов) пишутся в лог предупреждением, но граф
  всё равно рисуется и публикуется — как в relgraph.
- **Шрифты.** PNG рисуется Pillow, и ему нужен TTF-шрифт с кириллицей (Segoe UI,
  Arial или DejaVu). В slim-образе Debian/Ubuntu шрифтов нет — поставьте
  `fonts-dejavu-core`, иначе русские названия команд не отрисуются. Если шрифт
  не найден, бот пишет об этом при старте. SVG от шрифтов на сервере не зависит.
- Чтобы поменять `width` у уже стоящей картинки, верните маркер на её место.

### Переменные `.env`

| Переменная | Назначение |
|---|---|
| `CONFLUENCE_BASE_URL` | URL инсталляции, без завершающего `/` |
| `CONFLUENCE_PAT` | Personal Access Token (рекомендуется) |
| `CONFLUENCE_USERNAME` / `CONFLUENCE_PASSWORD` | Basic-авторизация, если нет PAT |
| `CONFLUENCE_VERIFY_SSL` | Проверять SSL (`false` для самоподписанных сертификатов) |
| `CONFLUENCE_CA_CERT_DIR` | Папка с корневыми (Root/CA) сертификатами для доверенной проверки TLS |
| `RULES_FILE` | Путь к файлу правил (по умолчанию `rules.yaml`) |
| `MOVE_CRON_SCHEDULE` | Расписание переносов, cron-выражение (по умолчанию `* * * * *`). Устаревший алиас — `CRON_SCHEDULE` |
| `MENTIONS_CRON_SCHEDULE` | Расписание сбора упоминаний. Не задано — наследует расписание переносов |
| `MENTIONS_DRY_RUN` | Пробный прогон только для сбора упоминаний. Не задано — берётся `DRY_RUN` |
| `GRAPH_CRON_SCHEDULE` | Расписание графа зависимостей. Не задано — наследует расписание переносов |
| `GRAPH_DRY_RUN` | Пробный прогон только для графа. Не задано — берётся `DRY_RUN` |
| `DRY_RUN` | `true` — только логировать, ничего не менять |
| `CONFLUENCE_QUERY_DELAY` | **Обязательно.** Минимальный интервал (сек) между запросами к Confluence — защита от HTTP 429. `0` — без паузы |
| `CONFLUENCE_MAX_RETRIES` | Сколько раз повторить запрос при 429 (по умолчанию `3`) |
| `CONFLUENCE_RETRY_MAX_WAIT` | Верхняя граница (сек) одиночного ожидания перед повтором (по умолчанию `60`) |
| `HEALTH_PORT` | Порт health-сервера в режиме демона (по умолчанию `8080`) |
| `HEALTH_LIVENESS_TIMEOUT` | Порог liveness (сек): дольше этого без признаков жизни — под перезапускается (по умолчанию `300`) |

> ID страницы виден в URL (`…/pages/viewpage.action?pageId=12345`) либо в
> «Page Information» → «Page ID».

### Задачи и расписания

Бот выполняет **задачи**, у каждой своё cron-расписание. Задача попадает в
расписание только если под неё что-то настроено в файле правил.

| Задача | Расписание | Включается секцией |
|---|---|---|
| `moves` | `MOVE_CRON_SCHEDULE` | `rules:` |
| `mentions` | `MENTIONS_CRON_SCHEDULE` | `mentions:` |
| `graphs` | `GRAPH_CRON_SCHEDULE` | `graphs:` |

Расписания стоит разнести. Переносы хотят частоты: страницу пометили `ready`, и
она должна уехать быстро, а холостой проход почти бесплатен. Сбор упоминаний
наоборот — читает тело каждой отобранной страницы и может её перезаписать,
поэтому `*/5 * * * *` для переносов и `0 * * * *` для сбора — разумная пара.

Расписание — обычное cron-выражение «мин час день месяц день_недели» в локальном
времени машины, где работает бот:

| Выражение | Когда |
|---|---|
| `* * * * *` | каждую минуту |
| `*/5 * * * *` | каждые 5 минут |
| `0 * * * *` | в начале каждого часа |
| `0 9 * * 1-5` | в 9:00 по будням |
| `0 9,18 * * *` | в 9:00 и в 18:00 |

Выражение проверяется при старте, при опечатке бот не запустится. Перед каждым
ожиданием он пишет в лог время следующего запуска и то, какие задачи на него
придут. Срок отсчитывается от текущего момента, а не от прошлого срабатывания:
если проход затянулся дольше промежутка между запусками, пропущенные сроки не
копятся — бот идёт к ближайшему будущему.

Отдельную задачу можно запустить флагом `--only`:

```bash
python -m confluence_label_bot --only moves --once
python -m confluence_label_bot --only mentions --once
python -m confluence_label_bot --only graphs --once
```

Планировать можно и снаружи — systemd timer или «Планировщик заданий» Windows,
запуская `python -m confluence_label_bot --once`.

#### Почему один процесс и один поток

Расписания разные, но задачи выполняются **последовательно в одном потоке**, и
это не упрощение, а требование. Защита от HTTP 429 держится на единственном
`CONFLUENCE_QUERY_DELAY` внутри клиента, а лимит Confluence — глобальный на
пользователя. Отдельные потоки поверх одного клиента ломают троттлинг (стреляют
одновременно), а отдельные процессы ломают его сильнее: пауза становится
локальной для каждого, и фактическая частота обращений оказывается кратно выше
заявленной. По той же причине не стоит разносить задачи по двум Deployment.

Когда сроки совпадают (`*/5 * * * *` и `0 * * * *` сходятся в начале часа),
задачи выполняются в порядке объявления: сначала переносы, затем всё остальное —
чтобы работать по уже устоявшемуся дереву.

### Троттлинг и защита от 429

Бот обходит поддерево по **одному запросу на страницу**, поэтому на больших
деревьях легко упереться в лимит Confluence и получить `HTTP 429 Too Many
Requests`. Обязательный `CONFLUENCE_QUERY_DELAY` задаёт минимальный интервал
между любыми двумя запросами: пауза добавляется, только если запросы идут чаще
(при редких запросах не тормозит). Значения `0.1–0.5` обычно достаточно; `0`
отключает паузу.

Если 429 всё же прилетел, бот повторяет запрос до `CONFLUENCE_MAX_RETRIES` раз,
уважая заголовок `Retry-After` (а без него — экспоненциальный backoff). Разовое
ожидание ограничено сверху `CONFLUENCE_RETRY_MAX_WAIT`, чтобы огромный
`Retry-After` не подвесил бота надолго.

### Health-check (Kubernetes)

В режиме демона бот поднимает лёгкий HTTP-сервер здоровья (stdlib, без внешних
зависимостей) на `0.0.0.0:HEALTH_PORT`:

| Эндпоинт | Проба | 200, когда |
|---|---|---|
| `GET /healthz` | liveness | главный цикл жив и не завис |
| `GET /readyz` | readiness | прошла стартовая проверка связи с Confluence |

Иначе — `503` с JSON-телом (у `/healthz` — возраст heartbeat).

В теле `/readyz` рядом с `ready` лежит результат последнего прогона каждой
задачи. Это справочная информация: **упавшая задача readiness не роняет** —
иначе сбой второстепенной задачи выводил бы из балансировки под, который
исправно делает всё остальное. Задача видна в выдаче с самого старта, ещё до
первого срабатывания своего расписания:

```json
{
  "ready": true,
  "tasks": {
    "moves": {"last_run_ok": true, "last_run_at": "2026-10-08T10:05:00", "last_error": null}
  }
}
```

**Важно про порог liveness.** Heartbeat означает «главный поток отвечает», а не
«давно ли был прогон»: бот обновляет его и во время работы, и во время сна между
запусками по cron. Поэтому `HEALTH_LIVENESS_TIMEOUT` **не зависит** от
расписаний задач — это «максимум, сколько главный поток может молчать». Ставьте
его с запасом на самый долгий одиночный запрос (timeout 30с + ретраи 429), а не
на интервал между прогонами. Будь порог привязан к интервалу, при редком
расписании (напр. `0 6 * * *`) перезапуск днём привёл бы к CrashLoopBackOff:
живой под спал бы до утра, а проба убивала бы его каждые несколько минут.

Пример проб в манифесте Deployment:

```yaml
        ports:
          - name: health
            containerPort: 8080
        livenessProbe:
          httpGet: { path: /healthz, port: health }
          periodSeconds: 30
          failureThreshold: 3
        readinessProbe:
          httpGet: { path: /readyz, port: health }
          periodSeconds: 30
        startupProbe:            # даём время на стартовую проверку связи
          httpGet: { path: /readyz, port: health }
          failureThreshold: 30
          periodSeconds: 5
```

Разовый (`--once`) и проверочный (`--check`) прогоны сервер не поднимают —
он нужен только долгоживущему демону.

### Корневые сертификаты

Если Confluence подписан внутренним корневым CA, положите его сертификаты
(`.pem` / `.crt` / `.cer` / `.der`) в папку (по умолчанию `certs/`, уже в
`.gitignore`) и укажите её в `CONFLUENCE_CA_CERT_DIR`. При старте все сертификаты
из папки собираются в единый бандл (вместе с `certifi`) и используются для
проверки TLS — отключать `CONFLUENCE_VERIFY_SSL` не нужно.

## Запуск

Активируйте venv (`.venv\Scripts\activate` / `source .venv/bin/activate`), затем:

```bash
python -m confluence_label_bot --check          # проверить правила и доступ к страницам
python -m confluence_label_bot --once           # один проход всех задач и выйти
python -m confluence_label_bot                  # демон (по расписаниям задач)
python -m confluence_label_bot --only mentions  # только одна задача (moves/mentions)
python -m confluence_label_bot --rules my.yaml  # другой файл правил
```

`--check` показывает расписание каждой задачи, проходит по всем правилам и
печатает заголовки страниц-источников и назначений — так сразу видно опечатку
в ID.

Начните с `DRY_RUN=true` и `--once`, чтобы увидеть, какие страницы будут перенесены,
без внесения изменений.

## Тесты

```bash
pip install -r requirements.txt -r requirements-dev.txt
pytest
```

Тесты не ходят в сеть: цикл демона прокручивается подменными часами, которые
вместо настоящего сна переводят время вперёд, поэтому проверки расписаний
выполняются мгновенно.

## Запуск как службы (systemd, пример)

```ini
[Unit]
Description=Confluence label mover bot
After=network-online.target

[Service]
WorkingDirectory=/opt/confluence-label-bot
ExecStart=/opt/confluence-label-bot/.venv/bin/python -m confluence_label_bot
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```
